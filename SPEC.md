# PReBi Reflection Week — Human vs. AI Feedback Challenge

## 1. Purpose
Build a responsive, German-language web app for an optional 3–5-minute activity at the PH Ludwigsburg Reflection Week booth. Visitors compare two feedback texts on the **same student reflection**: one authentic teacher-educator response and one independently generated AI response. They guess authorship, indicate which feedback they find more helpful, see the reveal and case-specific aggregate results, and may play another round.

The activity is a conversation starter about pedagogical feedback quality, **not** a validated AI-detection test or formal research instrument.

## 2. Users and devices
- Primary: visitors on their own phones via QR code, no login.
- Secondary: visitors using a shared booth laptop, with a prominent reset/new-visitor action.
- Responsive: stacked feedback cards on narrow screens; two columns on wide screens.
- Interface language: German. Code and developer documentation may be English.
- Accessibility: semantic HTML, keyboard support, readable contrast, large tap targets, visible focus, screen-reader labels, and non-color-only chart labels.

## 3. Visitor journey
1. **Welcome** — “Mensch oder KI? Feedback im Vergleich”; estimated duration, privacy note, start button.
2. **Case** — Show a short, approved reflection context. Present anonymized Feedback A and Feedback B with equivalent formatting and clearly separated paragraphs; allow scrolling and sufficient reading time.
3. **Vote** — Ask (a) “Welches Feedback stammt von Lehrenden?” A / B / “Ich bin unsicher”; (b) “Welches Feedback ist hilfreicher?” A / B / “Beide etwa gleich”. Both answers are required to submit; uncertainty is a valid authorship response. An optional multi-select (c) “Was macht Feedback X für dich hilfreicher?” (or, for “Beide etwa gleich”, “Was macht beide Rückmeldungen für dich hilfreich?” with base-form labels) offers up to three of seven fixed reasons: konkreter, persönlicher, fachlich genauer, klarer formuliert, ermutigender, benennt Schwächen ehrlicher, kürzer/auf den Punkt. There is deliberately no free-text field, so no personal data can be entered.
4. **Reveal** — Show which feedback was human-written, the participant’s answers, and a brief, carefully authored discussion prompt about feedback quality. Do not label a preference as right/wrong.
5. **Aggregate results** — Two case-specific charts: authorship guesses and helpfulness preferences. Show counts, percentages, and total responses; label small samples and avoid overinterpretation.
6. **Next action** — “Noch eine Runde?” selects an unplayed case when possible; “Fertig” ends the session. When all cases have been played, show a completion message and optional restart.

### Time target
One case should typically take 3–5 minutes. Do not use a timer or force quick decisions.

## 4. Case content and editorial rules
Use three curated cases initially. The development repository must contain **synthetic sample cases only** until anonymization, permissions, and institutional review are complete.

For production, each case should have:
- A short anonymized context for the original reflection (ideally 50–100 words).
- Two feedback responses addressing that same reflection.
- One response excerpted from authentic human teacher-educator feedback; one independently generated by AI from the reflection **without seeing the human feedback**.
- Comparable length, readability, and structure without misleading alterations to authentic feedback.
- A concise, manually authored reveal note and reflection question.
- Optional pedagogical metadata, e.g. Situationswahrnehmung (SW), Ursachenanalyse (UA), Handlungsalternativen (HA), for internal curation only.

Do not expose full source reflections, raw rubric packets, identifying metadata, unpublished annotations, or non-approved teacher feedback in public assets.

### Important architecture decision: answer secrecy
A static GitHub Pages app cannot securely hide a correct answer if the answer is shipped in browser JavaScript or public JSON. For the **local prototype**, use synthetic cases and client-side answer keys only. For the **production deployment**, serve the approved case text and A/B order from a server endpoint, and keep the correct answer and any nonpublic curation metadata on the server. The vote submission endpoint must derive the answer from the server's case record, not trust a browser-provided answer.

## 5. Randomization and session behavior
- Randomly choose one case at the start.
- Randomize the order of human/AI feedback independently for each round.
- Track case IDs already played in the current session and avoid repeats until all are exhausted.
- Save only ephemeral progress in memory or session storage as appropriate.
- A shared-laptop “Neue Person / Zurücksetzen” action clears local session progress and returns to the welcome screen.
- Do not use persistent identifiers or fingerprinting to identify visitors.

## 6. Frontend stack
- React, TypeScript, Vite.
- Simple, maintainable styling (plain CSS or a lightweight styling approach); no need for a large component framework.
- Charts: accessible CSS bars or a small chart library; always show numeric labels.
- Separate UI components, case types, API client, mock adapter, and production adapter.
- Keep the code suitable for static deployment to GitHub Pages; configure Vite `base` for the repository subpath.

Suggested structure:

## 7. Phase 1 — fully working local prototype (no backend)
Build and verify all screens using **clearly fictional** cases and simulated aggregate results. The mock API should have the same interface as the future production API.

Required behavior:
- Start, case display, voting, reveal, chart, next round, and reset all work.
- Feedback A/B order changes across rounds and is consistently respected in the reveal and charts.
- Simulated aggregate results are explicitly marked “Demodaten”.
- Votes cannot be submitted twice in one round through normal UI interaction.
- Handle empty, loading, and error states in the interface.
- Use no real student or educator content in test fixtures.

## 8. Phase 2 — Supabase integration
Use a Supabase project for shared anonymous votes and server-side case/answer handling. Prefer Edge Functions or equivalent controlled server endpoints:

### `start-round`
Input: optionally a list of case IDs already seen in the current session (untrusted, bounded).
Output: opaque round token, case ID, approved reflection context, Feedback A and B, no authorship labels. Server securely binds token to case ID and randomized presentation order. Token must be integrity-protected or backed by short-lived server state; do not expose answer mappings in a decodable unsigned token.

### `submit-vote`
Input: round token, authorship guess (`A`, `B`, `unsure`), helpfulness preference (`A`, `B`, `equal`), optional helpfulness reasons (a duplicate-free subset of at most three of `concrete`, `personal`, `precise`, `clear`, `encouraging`, `honest`, `concise`), and a per-round idempotency key. Stored reasons are `NULL` when not asked (legacy votes and older clients) and `{}` when asked but none selected.
Server: validate inputs and token, derive the correct A/B mapping, enforce idempotency, apply reasonable abuse controls, insert one vote, then return correct authorship and aggregated counts. Do not trust client-supplied answer keys.

### `get-results` (optional)
Input: case ID, subject to reasonable request controls.
Output: aggregated case-specific counts only; no raw vote rows.

### Database
Use a private `cases` table for approved case content and answer mappings, and a private `votes` table containing only the fields necessary to count responses. Suggested vote columns: `id`, `case_id`, `presentation_order`, `authorship_guess`, `helpfulness_preference`, `created_at`, and an idempotency key or its hash. Store the order so results can be normalized to human vs. AI, while the UI may also show A vs. B for the participant's specific round.

Enable Row Level Security; do not grant anonymous browser clients direct select/insert access to raw votes or private cases. Use server-side functions with narrowly scoped database access. Secret/service-role keys remain server-side only. The frontend may use the public Supabase URL and publishable key as appropriate. Configure CORS for local development and the deployed site.

### Privacy and integrity
- No login, names, email addresses, personal reflection uploads, persistent tracking IDs, or analytics by default.
- Inform visitors that anonymous choices are stored and aggregated.
- Decide retention period and obtain institutional privacy approval before public deployment.
- A public anonymous poll cannot reliably guarantee one person/one vote; implement reasonable rate limits and idempotency without claiming research-grade validity.
- If backend is unavailable, show a clear error and offer a non-submitting demonstration mode rather than pretending votes were saved.

## 9. Hosting and configuration
- Frontend: GitHub Pages, built with GitHub Actions or another documented deployment workflow.
- Backend: Supabase cloud.
- Environment variables: `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (or a documented API base URL). Never use `VITE_` variables for secrets.
- Include `.env.example`, `.gitignore`, and a setup guide.
- Do not commit real case material before approval.
- Test on HTTPS deployment, at narrow mobile widths, and on the booth laptop.
- Prepare an offline/non-voting fallback if connectivity fails.

## 10. Acceptance criteria
- A new visitor can complete one round without login in approximately 3–5 minutes.
- The app works on phone and laptop; laptop can reset completely for the next visitor.
- Case selection and A/B placement are randomized; repeat cases are avoided in-session.
- The reveal is correct regardless of feedback placement.
- Aggregate charts are based on the **same case** and use the correct A/B-to-source normalization.
- The production browser cannot fetch correct authorship before submitting a vote.
- Multiple browsers can submit and see updated totals.
- A repeated submission with the same idempotency key is not counted twice.
- No private keys, source reflection files, or unapproved teacher feedback are in public assets.
- Loading, API failure, and zero-vote states are handled clearly.

## 11. Copilot implementation instructions
Implement **Phase 1 only** first. Do not create Supabase resources, credentials, or production endpoints yet. Begin by scaffolding React + TypeScript + Vite and building the entire visitor journey using synthetic German-language cases and a mock API. Add basic automated tests for randomization, reveal correctness, repeat prevention, and session reset. Document local startup commands (`npm install`, `npm run dev`, `npm run build`). Once Phase 1 is reviewed, proceed to Phase 2 in a separate task.

## 12. Open decisions before public launch
- Final number of cases and editorial approval of excerpts.
- Consent/permission to publicly show teacher feedback and student reflection contexts.
- Institutional privacy review, retention, and hosting approval.
- Whether the booth should display an optional aggregate dashboard.
- Moodle/AskAlma continuation URL and final poster/QR copy.
